STAGE 4: ENet/RPC-compatible headless Godot server (desktop test)

Почему это нужно:
Stage 3 Kotlin UDP/JSON НЕ совместим с Godot ENet + MultiplayerAPI RPC.
Этот тестовый сервер запускает ТОТ ЖЕ Net.gd внутри отдельного Godot-процесса.
Поэтому соединение и RPC имеют тот же формат, что и у существующего клиента.

Тест на компьютере с установленным Godot 4.x:
1. Открыть проект WiFiLobby в Godot.
2. Запустить в терминале из каталога проекта:
   godot --headless --path . --scene res://server/headless_server.tscn -- --port=24567
3. На другом экземпляре игры нажать Online Join и подключиться к IP компьютера, порт 24567.
4. Для подключения из другой сети нужен доступный UDP-порт/Relay.

ВНИМАНИЕ:
- Это отдельный headless процесс для проверки совместимости RPC, не Android Foreground Service.
- Существующий Net.gd поддерживает только MAX_PLAYERS=2 и при выходе клиента закрывает лобби.
- Сохранение каждые 60 секунд есть, но восстановление игроков и авторизация UUID не интегрированы.
- В боевой сцене остаётся игровая логика, не перенесённая в отдельный сервер.
- Headless host не создаёт полноценный Battle scene и не симулирует бой.
- Kotlin Android Service из Stage3 остаётся прототипом и НЕ запускает Godot headless.
- Для реальной фоновой Android-работы требуется встроить совместимый серверный runtime,
  переделать сетевую модель и проверить ограничения Android на реальном устройстве.
- APK не собран, тест на устройстве не проводился.

Следующие этапы: выделение авторитетной логики из battle.gd, persistent player ID
с подтверждением владения токеном, восстановление snapshot с миграцией peer IDs,
подключение Android Foreground Service к совместимому runtime, аппаратные тесты.
